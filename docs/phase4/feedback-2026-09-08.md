# 2026-09-08 冷启动与后台恢复卡顿修复记录

## 背景与范围

邮件报告版本为 2.1.9，设备为 vivo X90、Android 16、天玑 9200。
用户称打开应用后点击底部导航切换页面会卡顿，冷启动可稳定复现，
退出到后台再进入也能触发。共有 4 个订阅，但未提供每份订阅的节点数量。
开发者自己的普通订阅未复现，因此大节点数据量是排查假设，并非已确认事实。

另有立即点击“启动”后偶发自动关闭的报告，正文未明确是 VPN 停止还是应用退出。
本次只修复明确的初始化时序缺陷，不据此宣称解决了所有可能的闪退。
蓝白配色和连接状态颜色不在本次修改范围。

## 已确认的代码问题与修改

1. **列表提前创建所有展开节点的 Widget。**
   原先 `ListView.builder` 外部先调用 `_buildItems`，创建全部节点卡片，
   再遍历 Widget 计算组标题位置。即使屏幕只显示少量节点，准备工作仍随展开节点总数增长。
   现在只记录每个组的起始行和高度，按视口请求创建卡片；二分查找行所属的组。
   同时提供行高，跳转远处节点时不必通过构建中间卡片推算尺寸。
   标题、展开/折叠、选中节点跳转和行圆角的语义保留。

2. **数据库后台执行不等于模型转换也在后台执行。**
   原来的 Drift `GroupsConverter` 在调用侧进行整份快照的 JSON 编解码和模型转换。
   现在 DAO 读写原始 JSON 字符串，在 isolate 中完成转换。
   表结构、快照版本、数据格式和所属 Profile 的事务保护保持兼容，无需数据库迁移。

3. **进入代理页重复读取旧快照。**
   原先页面初始化无条件恢复磁盘快照，即使已有当前订阅的代理组。
   现在仅在当前订阅的数据缺失时恢复，避免重复解析、发布和旧数据覆盖。

4. **大配置解析与文件校验占用 UI 线程。**
   Provider 存在性检测会解析整份 YAML；源配置保留流程同样直接解析 YAML；
   快照指纹计算直接对整个配置文件计算 SHA-256。
   这些计算移到后台 isolate，文件内容、解析规则和指纹算法不变。
   运行时代理组转换原本已使用 `compute`，没有重复改造。

5. **早期用户启动与应用初始化可能交叉。**
   首页原来以 `isInit: !initProvider` 调用启动：初始化未结束的用户点击被当成自动启动，
   可能与原生会话恢复和初始化配置操作同时执行。
   现在 `GlobalState.attach` 合并并发初始化；首页等待初始化完成后按用户操作启动。
   若恢复后的状态已满足这次请求，则不重复执行启动/停止。
   初始化失败时不会把等待者当作已就绪放行。

## 结论与复测边界

这是对确定存在的 UI 线程重计算、重复快照恢复和初始化时序问题的修复。
单元与组件测试不能证明反馈者设备上的帧率提升；没有提供 FPS、卡顿百分比或耗时改善数字。
没有取得用户实际订阅、现场性能轨迹，也没有在该 vivo X90 上复测。

后续真机验收应覆盖普通订阅和千节点订阅：冷启动立即切换底部导航、HOME 后恢复再切换、
展开/折叠代理组与跳转选中节点，以及初始化期间点击启动。
性能数据应取 profile 或 CI release APK；debug 只用于功能诊断。
若仍卡顿，应采集对应操作的 Flutter FrameTiming / Timeline 和原生日志，
进一步区分 UI 计算、布局绘制和设备渲染问题。
