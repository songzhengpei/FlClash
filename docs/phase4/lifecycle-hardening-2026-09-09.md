# 2026-09-09 启动、恢复、暂停与停止时序加固报告

## 背景和结论

本轮承接 2026-09-08 邮件反馈及其后的代码时序审计。反馈版本为 2.1.9，设备为 vivo X90 / Android 16 / 天玑 9200：冷启动后页面切换卡顿、从后台回到前台卡顿，以及刚打开应用立即启动时偶发“自动关闭”。邮件提及 4 个订阅，但每份订阅的节点数量未知；大订阅是排查假设，不能写成已确定的根因。“自动关闭”也没有足够证据区分 VPN 停止与应用进程退出。

本轮修复审计列出的 8 类时序缺陷，并合入上一轮尚未提交的性能修复。核心规则为：原生会话管理实际资源，Flutter 投影会话状态；新用户意图使旧工作失效；停止不等待 Flutter 的旧启动准备；Go 操作完成前不能提前释放原生生命周期锁。

没有改动蓝白配色。此次没有在反馈者的 vivo 手机上复现或复测，也没有测量生产 APK 的帧耗时，因此不宣称已经证实所有原始现象消失。

## 审计问题与修复对应

| 优先级 | 问题与触发时序 | 修改后的行为 |
| --- | --- | --- |
| 高 | 原生启动成功后立即进入智能暂停，Flutter 读到 PAUSED，却把它当作启动失败并执行完整停止 | 原生启动确认同时接受 RUNNING / PAUSED。Android CoreLib 直接委托原生启动；Flutter 根据真实快照显示运行或暂停，不再因布尔失败或未确认结果盲目停止服务 |
| 高 | 旧智能恢复结束时，用户已停止；恢复兜底再次调用完整启动 | Android 智能恢复只发 smartResume 并重新读取状态；失败不会偷偷转为完整启动。Flutter 生命周期代次使过期启动准备、配置预加载和恢复后续失效；原生排队命令也检查意图代次 |
| 高 | 等待权限期间，状态同步将 PENDING 写成 STOP，权限成功后启动被取消 | 应用侧单独保存权限启动的 pendingStartEpoch 和 stopEpoch；提交资格依赖用户意图，不依赖被快照覆盖的 RunState。显式停止立即使旧权限结果失效 |
| 高 | quickSetup 在原生锁外执行，旧完成回调将新会话写成 STOPPED | quickSetup 在原生会话锁内等待 Go 完成；仅接受仍然有效的停止态准备请求。失败不伪造物理停止。恢复准备结束后重新检查恢复代次；Go 的初始化与配置准备在同一把锁内完成 |
| 中 | Flutter 的状态“同步”实际会关闭 Go 监听器，旧 STOPPED / PAUSED 快照破坏新会话 | 同步改为纯 UI 投影，不发送监听器停止、流量重置等核心命令。快照读取有请求序号和生命周期代次保护，过期读取不继续投影 |
| 中 | 自动恢复只恢复 TUN，手动恢复另外启动监听器，两条路径不对称 | VpnService / CommonService 在物理生命周期互斥锁内管理 Go 监听器。VPN 启动和恢复先确认监听器，再建立 TUN；暂停停止监听器和 TUN。自动策略与手动操作共用同一组物理方法 |
| 中 | 完整停止后的异步 closeConnections / GC 可能清理新会话 | Go 停止监听器时在 runLock 内关闭连接。完整停止的统计重置和 GC 在原生会话锁内等待完成；Flutter 不再发脱离生命周期的延迟清理。网络切换清理也改为等待确认 |
| 中 | Go 的 isRunning / isInit、quickSetup、shutdown 使用不一致的锁 | 初始化、配置准备、监听器启停、状态读取和 shutdown 共用 runLock；内部 locked 方法避免重复加锁。quickSetup 仅准备配置，不表达启动意图；配置后的内存回收仍在锁释放后执行 |

## 额外加固

- 所有普通 Flutter 启动入口统一等待 `globalState.attach()`，覆盖首页之外的磁贴入口。首页点击立即登记意图，不在组件层先等待 attach 或延迟提交。attach 本身为 singleflight，失败后可以重试。
- Flutter 停止立即使旧配置请求失效，并绕开旧启动准备队列执行原生停止。磁贴停止不再因为 UI 尚未显示运行而直接丢弃。
- 冷启动遇到已有 PAUSED 会话时，即使启用了 autoRun，也保留暂停；遇到 STARTING / STOPPING 时只连接并同步，避免再发起竞争性的完整配置启动。
- 异步流量读取会检查启动代次、开始时间及统计计时器条件，防止停止后旧采样重新填回界面。
- 智能暂停状态持久化失败会回滚物理状态；如果物理回滚也失败，转入完整停止收敛，而不是继续宣称旧状态仍然成立。
- 原生 Go 生命周期回调采用不可取消的等待区间：外层请求超时或取消，不代表 Go 已终止。等待确认之后才释放生命周期锁，防止旧 Go 操作越过下一条命令。
- Android `onDestroy` 的有界主线程清理不等待 Go 回调；异常断连后的监听器清理由原生后台路径在会话锁和 delegate 身份检查下执行。
- 移除 VpnService 销毁末尾无条件重复 `stopTun`，并让撤销 VPN 的清理在会话身份检查之后执行，缩小旧服务清理影响新会话的窗口。

## 修复后的主要链路

| 入口 / 已有状态 | 时序与结果 |
| --- | --- |
| 手动启动，STOPPED | 等待 attach → 确认核心可用 → 配置准备 → 校验启动意图 → 权限准备 → 原生串行建立监听器和 TUN → 读取 RUNNING 或 PAUSED |
| 启动过程中点击停止 | 立即提升停止代次并使旧配置请求失效 → 原生停止 → 更新 UI；旧权限或配置返回时不得重新提交启动 |
| 正在运行，再次启动 | 原生检查实际资源是否仍工作；可复用时确认现有会话，不仅凭缓存 RUNNING 作判断 |
| 智能暂停 | 原生策略或手动命令 → 同一物理 smartStop → 提交 PAUSED → Flutter 显示暂停 |
| 智能暂停后恢复 | 自动策略和手动 smartResume 均恢复监听器与 TUN → 确认物理状态 → 提交 RUNNING；失败保留实际状态，不自动发起另一条完整启动 |
| 从后台进入 | 同步原生快照并更新计时器、界面；同步本身不关闭或重开代理 |
| 冷启动发现 PAUSED | 连接核心并恢复显示所需配置，保留暂停意图 |
| 冷启动发现 STARTING / STOPPING | 连接并观察已有过渡；后续原生生命周期信号负责 UI 收敛 |
| 手动停止，RUNNING / PAUSED / 启动等待 | 原生停止实际资源，等待连接清理、统计重置；确认 STOPPED 后更新 UI |
| 进程恢复与用户停止交叉 | 恢复检查点与恢复代次继续作为约束，quickSetup 返回后再次验证；过期恢复不得建立新会话 |

## 对“刚打开就启动，偶发自动关闭”的具体作用

本次针对的是可以从代码证明存在的错误链，而不是推测厂商原因：

1. attach 未结束就开始启动，现已统一等待。
2. 权限对话框期间正常状态同步使启动资格丢失，现由独立意图代次决定资格。
3. 刚启动就因可信网络进入 PAUSED，原先会被误当失败再停止，现接受该合法结果并显示暂停。
4. 超时、取消或晚到回调原先可能越过下一条命令，现等待核心操作确认并过滤过期后续。
5. 失败不再触发未经确认的完整停止或智能恢复后的隐式完整重启。

这些修改能排除上述代码路径造成的误停与错误恢复；没有反馈设备日志或复测结果时，仍不能把进程闪退、系统撤销 VPN、厂商后台限制等不同原因一并宣告解决。
